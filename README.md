# 標準開発テンプレート

Claude Codeでの開発を「後付け・手戻り」に陥らせないためのガードレール一式。
**要件の確定 → 設計 → 実装** の順を、忘れようがない場所に固定して配る。

## なぜ「貼るプロンプト」ではなくテンプレートなのか

失敗は**バグ報告を受けた瞬間**に起きる。その瞬間に自動で読み込まれる場所
（`CLAUDE.md`・スキル）にルールが無ければ効かない。手で貼る方式は、貼るのを
忘れた時＝急いでいる時にこそ効かない。

実例: あるプロジェクトでは、継ぎ足し修正の原因が**`bugfix`スキルに
「最小修正。周辺の気になる箇所は触らず報告のみ」と書いてあったこと**だった。
不具合報告のたびに自動で読まれるので、手順どおりに継ぎ足しが起きていた。
ガードレール自体が原因側にあった、という構図。

## 中身

```
global/                      → ~/.claude/ へ配る（全プロジェクトに効く）
  CLAUDE.md                  判断基準の要約（常時読み込み）
  skills/requirement-driven/ **方法論の正**。フェーズ0〜4と成果物の契約
project/                     → 各プロジェクトへ配る
  CLAUDE.md.template         プロジェクト用のひな型（穴埋め式）
  skills/SKILL.md.template   プロジェクト固有スキルのひな型（導線入り）
導入プロンプト.md             既存プロジェクトへ導入するときの貼り付け文
適用.ps1                      配布・回収スクリプト
.github/workflows/validate.yml テンプレート構造の検証（CI）
```

## 使い方

### 全プロジェクトへ適用（初回・更新時）

```powershell
cd C:\Claude\dev-template
.\適用.ps1 -Global
```

`~/.claude/` の既存ファイルは `~/.claude/_backup_<日時>/` へ退避してから上書きする。

### 新規プロジェクトを始めるとき

```powershell
.\適用.ps1 -Project C:\Claude\新プロジェクト
```

`CLAUDE.md`（ひな型）と `.claude/skills/` を用意する。**ひな型は穴埋め式**なので、
最初のセッションで実際の内容に置き換えること。

### 運用中に `~/.claude/` を直接直したものを取り込む

```powershell
.\適用.ps1 -Collect
```

`~/.claude/` の内容を `global/` へ戻す。差分を確認してからコミットする。

## 既存プロジェクトへ導入するとき

`導入プロンプト.md` にそのまま貼れる文面がある（開発途中から入る場合／新規の場合）。
開発途中から入る場合は、**当たりをつけて理解を先に提示させ、すり合わせる**のが要点。

## 運用モデル（聖典・配布物・現場）

| 役割 | 実体 | 扱い |
|---|---|---|
| **聖典** | `global/skills/requirement-driven/` と `global/CLAUDE.md` | 標準。全プロジェクトの土台 |
| **配布物** | このリポジトリ | 聖典を配る手段。テンプレートでしかない |
| **現場** | 各プロジェクトの `CLAUDE.md`・`.claude/skills/` | **どの要素も自由に追記・編集してよい** |

現場での改変は歓迎する。プロジェクトごとに事情は違うし、**そこで初めて分かることがある**。
そのうえで、**標準化すべきと判断したものだけを聖典へ昇格させる**。

### 昇格の手順

1. 現場で改変する（プロジェクトの `CLAUDE.md` か `.claude/skills/`）
2. しばらく運用して、**他プロジェクトでも通用するか**を見極める
3. 通用すると判断したら `global/` 側へ反映し、コミットする
   （何のプロジェクトで何が起きて昇格させたのかをコミット本文に書く）
4. `.\適用.ps1 -Global` で全体へ配る

逆に**プロジェクト固有の事情に依存するものは昇格させない**。聖典が個別事情で
膨らむと、どのプロジェクトでも読み飛ばされる置物になる。

### ただし: 同名スキルは聖典を覆い隠す

プロジェクト側に聖典と**同じ名前**のスキルを置くと、そのプロジェクト内では
プロジェクト側だけが読まれ、**聖典は読まれない**。追記したつもりが差し替えになる。

これは仕組み上の挙動なので、プロジェクト固有スキルは必ず
`.\適用.ps1 -Project <パス> -Skill <名前>` で作ること。
**聖典を先に読ませる導線が入ったひな型**が生成される。手書きしないこと。

## 3層構造

| 層 | 場所 | 効き方 |
|---|---|---|
| 1 常時ガードレール | `~/.claude/CLAUDE.md` | 全プロジェクト・全セッションで自動読込。最強 |
| 2 手順書（**方法論の正**） | `~/.claude/skills/requirement-driven/` | 必要時に読み込み。1の肥大を防ぐ |

**同じ規則を2箇所に書かない。** 1は判断の起点だけを持ち、手順の詳細は2に置く。
`導入プロンプト.md` は起動装置であって方法論ではないので、手順を写さないこと。

### 0層: フック（`global/hooks.json`）

`UserPromptSubmit` で毎ターン短い確認文を注入する。**何もブロックしない**ので
誤検知の代償がゼロ。`適用.ps1 -Global` が `~/.claude/settings.json` の
`hooks` キーだけを差し込む（**丸ごと上書きしない**。他の設定を壊さないため）。

**入れた根拠**: 当初「未観測の制約への先回りになる」として見送り、
「フェーズ宣言が出続けるか」を観測することにした。結果:

| セッション | 観測 |
|---|---|
| music-watch | 宣言が出続けた |
| file-organizer | **長い作業の後半で減衰した**。要件整理の直後に消える |

同時に、**規則を作った当人が次の案件で自分に適用しない**という失敗が
2セッションで起きた（music-watch の「規則は持っていたのに自分の出力に当てて
いなかった」と同型）。n=2 で条件が揃ったため導入した。**推測ではなく観測で
決めた**という順序が重要で、これを崩すとテンプレート自身が規則を破ることになる。

以前は「Claude Code以外で使う保険」として3層目（携帯用プロンプト）を置いていたが、
**Claude Code以外を使う予定が無いと確認できた**ため削除した。存在しない制約に
備えた要件だった（2026-08-02）。

## 注意: `.ps1` は BOM付きUTF-8 で保存する

Windows PowerShell 5.1 は `.ps1` を既定でANSIとして読むため、**BOMが無いと日本語が
壊れて構文解析に失敗する**（`適用.ps1` は BOM付きで保存済み）。編集ツールによっては
BOMが落ちるので、日本語を含む変更をしたら先頭バイトを確認すること。

```powershell
[System.IO.File]::ReadAllBytes('.\適用.ps1')[0..2]   # 239 187 191 (EF BB BF) ならOK
```

## リモート

**このリポジトリはGitHubに置いてよい**（https://github.com/yupiteru2/dev-template）。
中身が汎用の開発ルールのみで、NASパス・作品名・購入履歴といった個人情報を
一切含まないため。CIもここで回している。

**他のプロジェクトは同じ扱いにしないこと。** 個人情報を含むものはWebリモートへ
pushせず、ローカルまたは家庭NASのbareリポジトリへ。

```powershell
git clone --bare C:\Claude\<プロジェクト> \\NAS\backup\<プロジェクト>.git
git remote add nas \\NAS\backup\<プロジェクト>.git
```

判断基準は「Webに置くな」ではなく**「個人情報を外部に出すな」**。
禁止の形で覚えると、安全なものまで手段を失う。

### push時の検証（任意）

単独開発で外部CIを持たないプロジェクトでは、`pre-push`フックに検証コマンドを
入れておくと「壊れたコードを本流に入れない」を確保できる。file-organizerに実装例あり。
ただし**pushしない限り発火しない**ので、bareリポジトリを作って初めて効く。
