# 開発共通ルール（全プロジェクト適用）

プロジェクトの CLAUDE.md と矛盾する場合はプロジェクト側が優先。

本ファイルと skill: requirement-driven の出所は **`C:\Claude\dev-template`**
（GitHub: yupiteru2/dev-template）。プロジェクト固有の改変は自由だが、
**他プロジェクトでも通用すると分かったものは同リポジトリへ昇格させる**
（手順は README「昇格の手順」。プロジェクト固有の事情に依存するものは昇格させない）。

## 全体の流れ

要件の確定 → 設計 → 実装 → セルフレビュー → 検証 → コミット。

フェーズごとにモデルを替える: 調査=sonnet／設計判断=opus／実装・テスト=sonnet／
受け入れ確認=opus（各フェーズの成果物は skill: requirement-driven を参照）。

## 1. 要件の確定（最重要。ここを飛ばすと後が全部ずれる）

**まず層を分ける。** 混ぜると聞き方が平板になる。

| 層 | 何か | 変わるか |
|---|---|---|
| **軸** | アプリ全体で叶えたいこと | **変わらない**。変わったら別のアプリ |
| **制約** | 環境・コスト・技術・運用上の制限 | 変わりうる |
| **要件・実装** | 軸を制約下で実現した形 | 制約が変われば変えてよい |

**要件は制約によって歪む。歪むこと自体は正しい。** 問題は歪んだ形が軸として
扱われること。診断は **「その制約が消えたら、この要件はどう変わるか？」**
——変わらなければ軸に近い。形が変わるなら制約由来の歪みで、聖域にしてはいけない。
実例:「LLM禁止」は、軸が「人手をかけず正しく収める」、制約が「継続課金の回避」で、
禁止は歪んだ要件だった（ローカルLLMは可）。

- 曖昧なまま着手しない。**新規なら真の要件を定義できるまで詰める**。
  開発途中からなら、既存の実装・文書から**当たりをつけて提示し、すり合わせる**
- 「なぜそれが必要か」で1段上げる。**禁止・制約の形で語られたものは特に疑う**
- **例外と「ただし」を必ず聞く**（一括適用してよい範囲／人の確認が要る範囲はどこか）
- 具体例を1つ出してもらい、**こちらから境界事例を作って**認識を突き合わせる
- 事実で決められることは実データで確かめる。推測で要件を埋めない。
  ただし**実測から要件を導かない**（実測は検証手段であって根拠ではない。
  「今こうなっている」は「こうあるべき」ではない）
- 分からないことは「不明」と書く。決めつけない
- **確定した規則は要件文書に書いて初めて確定**とする

## 2. 設計（問題対応もここから始まる）

- 症状を見つけても**いきなり最小修正しない**。単発か構造かを仕分ける。
  複数症状／再発／「前も直した」／修正が2箇所以上に散る、なら要件から設計し直す
- 症状を並べる前に「**どの要件が書かれていなかったか**」を言語化する。個々の症状は
  たいてい共通の要件未達の別の顔。よくある形は §1 の「制約由来の歪み」と、
  要件が不変条件ではなく**安価な代理指標**で書かれていた場合
  （例: 巻数をファイル件数で代理／キャッシュの妥当性をI/O回数で代理）
- **重要度つき修正リスト（A→B→C）を出して着手可否を聞かない。** 着手順は設計から導出する
- **サンクコストで歪めない。** 何が正しいかの判断を既存コードの形に合わせない
  （§3の「変更範囲を最小化」は実装の話であり、設計の話ではない）。
  迷えば同一要件におけるデファクトを採る
- **応急処置・暫定対応は既定で行わない**（明示要求時のみ）

## 3. 実装

- 既存設計を尊重し変更範囲を最小化。要求範囲外の変更・不要なリファクタリング禁止
- YAGNI / KISS。DRYは守るが過度な抽象化は禁止。既存ライブラリ・既存コードを優先
- **TDDは既定で行わない。** 行うのは次のみ：明示要求／アルゴリズム・計算ロジック・
  状態遷移・認証／重大なバグ修正・リグレッション防止。テストコードもその場合のみ生成する。
  テスト名は日本語で仕様を表す（例: `test_巻数なしは単巻扱い`）。
  バグの回帰は実入力のまま固定する

## 4. 検証とコミット

- セルフレビュー: バグ／境界条件／例外処理／命名／責務分離／保守性／不要な複雑化／
  パフォーマンス。問題は直してから、**修正後の完成版のみ**提示する
- **サブエージェントの報告した数値は自分で再測定してから採用する**
- 検証（テスト・リンタ・型・実動作）を通してからコミット。
  メッセージは日本語1行（必要なら本文追加）

## セッション運用

- 中間生成物・途中経過・思考過程は出力しない。最終結果のみ簡潔に。
  説明よりコードにトークンを使う
- 「再開して」＝上限回復による再開。**それまでの方針を維持**し、指示されていない配慮
  （トークン節約・成果分割・検証の後回し）を勝手に足さない

## 安全原則

- ユーザーデータを壊しうる操作（上書き・削除・一括変更）は実行前に確認を取る。迷ったら安全側で報告
- 認証情報・個人情報をコード・ログ・コミットに含めない
