# 要件駆動プロンプト（携帯用・3層目）

Claude Code以外（Web版・他ツール・他人への依頼）で使う保険。
Claude Codeでは `~/.claude/CLAUDE.md` と skill: requirement-driven が自動で効くため不要。

---

## A. 着手時に貼る（新規・仕様変更）

```
着手する前に、私の要求の裏にある「真の要件」を確定させてください。

私が語る要求は、真の要件の誤った具体化であることがあります。特に「〜するな」
「〜は使うな」という制約・禁止の形で伝えたものは、目的ではなく手段を言っている
可能性が高いので疑ってください。

進め方:
1. 「なぜそれが必要か」を1段上げて確認する。目的が分かれば別の手段が使えることが多い
2. 例外と「ただし」を必ず聞く。一括適用してよい範囲と、人の確認が要る範囲を分ける
3. 私に具体例を1つ出させ、そこからあなたが境界事例を作って認識を突き合わせる
4. 事実で決められることは実データで確かめる。推測で要件を埋めない
5. 分からないことは「不明」と書く。決めつけない

要件が定義できるまで実装に入らないでください。既に開発途中の場合は、既存の実装や
文書から当たりをつけて「こう理解しているが合っているか」の形で提示し、すり合わせて
ください。確定した要件は文書に書き出してください。
```

## B. 不具合・課題の対応時に貼る

```
このバグ／課題を最小修正で済ませないでください。

まず「どの要件がどこで満たされていないか」を整理してください。症状を並べる代わりに
「どの要件が書かれていなかったか」＝要件の空白を言語化してください。個々の症状は
たいてい共通の要件未達の別の顔です。よくある形は「要件が本来の不変条件ではなく、
安価な代理指標で書かれていた」というものです。

そのうえで「どうあるべきか」を設計し、着手順は設計から導出してください。
重要度つきの修正リスト（A→B→C）を出して着手可否を聞くのは禁止です。それは症状に
順番を付けただけで、継ぎ足し修正が続きます。

制約:
- 既存コードの形に合わせない。迷ったら同一要件のデファクトを採る。サンクコストは
  判断材料にしない
- 応急処置・暫定対応は、私が明示的に頼むまで提案しない
- 同じ規則が既に別の場所に実装されていないか探す。あれば写経せず1箇所に集約する
- 新しい規則は要件文書に追記して初めて確定とする

調査や実装を他のエージェントに任せた場合、報告された数値は自分で再測定してから
採用してください。受け入れ確認では変更前後を同一手法で測り、可能なら変更前で
不具合を再現してから対比してください。
```

## C. 途中で継ぎ足しに戻りかけたとき

```
それは症状への後付け対応になっていませんか。要件に立ち返って、どうあるべきかから
設計し直してください。
```

---

## 補足: なぜ「貼るプロンプト」が最下層なのか

失敗は「バグ報告を受けた瞬間」に起きる。その瞬間に自動で読み込まれる場所
（CLAUDE.md・スキル）にルールが無ければ効かない。手で貼る方式は、貼るのを忘れた
時＝急いでいる時にこそ効かない。あくまで自動化できない環境向けの保険とする。
